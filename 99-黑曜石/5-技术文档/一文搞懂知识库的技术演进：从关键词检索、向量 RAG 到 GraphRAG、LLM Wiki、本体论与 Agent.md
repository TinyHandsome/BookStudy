| 阶段                | 增加的能力                         | 典型问题                                   |
| ------------------- | ---------------------------------- | ------------------------------------------ |
| 关键词检索          | 匹配明确词语                       | “文档里有没有这句话？”                     |
| 全文搜索与索引      | 搜索大规模文本并利用字段筛选       | “哪些资料包含这些词，且属于这个部门？”     |
| 向量检索            | 按语义相似度找文本                 | “没有用同样的词，能否找到相关内容？”       |
| RAG                 | 把检索结果交给模型生成回答         | “能否根据公司资料回答问题并引用依据？”     |
| 混合检索与重排序    | 结合多种召回方式，优化候选结果次序 | “怎样提高召回率和最终上下文相关性？”       |
| 知识图谱与 GraphRAG | 表达实体关系，并沿关系查找信息     | “这个项目、客户、合同和产品如何关联？”     |
| LLM Wiki            | 把新资料融入可持续更新的知识页面   | “能否复用之前整理出的跨文档结论？”         |
| 本体论与语义层      | 明确业务概念、关系和约束           | “不同系统里的‘客户’究竟是不是同一个概念？” |
| Agent               | 让模型调用工具并完成流程           | “能否查状态、核权限并执行下一步操作？”     |

## 1. 关键词检索：从“记得文件名”到“搜得到词”

**关键词检索适合术语明确、目标清楚的查询**，但它不擅长处理表达方式变化和隐含语义。

![image-20261020085117221](%E4%B8%80%E6%96%87%E6%90%9E%E6%87%82%E7%9F%A5%E8%AF%86%E5%BA%93%E7%9A%84%E6%8A%80%E6%9C%AF%E6%BC%94%E8%BF%9B%EF%BC%9A%E4%BB%8E%E5%85%B3%E9%94%AE%E8%AF%8D%E6%A3%80%E7%B4%A2%E3%80%81%E5%90%91%E9%87%8F%20RAG%20%E5%88%B0%20GraphRAG%E3%80%81LLM%20Wiki%E3%80%81%E6%9C%AC%E4%BD%93%E8%AE%BA%E4%B8%8E%20Agent.assets/image-20261020085117221.png)

## 2. 向量检索：从匹配词语到匹配语义

向量检索解决的是**如何召回可能相关的文本**，不是**如何验证文本是否符合业务规则**。

![image-20261020085448855](%E4%B8%80%E6%96%87%E6%90%9E%E6%87%82%E7%9F%A5%E8%AF%86%E5%BA%93%E7%9A%84%E6%8A%80%E6%9C%AF%E6%BC%94%E8%BF%9B%EF%BC%9A%E4%BB%8E%E5%85%B3%E9%94%AE%E8%AF%8D%E6%A3%80%E7%B4%A2%E3%80%81%E5%90%91%E9%87%8F%20RAG%20%E5%88%B0%20GraphRAG%E3%80%81LLM%20Wiki%E3%80%81%E6%9C%AC%E4%BD%93%E8%AE%BA%E4%B8%8E%20Agent.assets/image-20261020085448855.png)

## 3. RAG：检索结果进入模型上下文

RAG 答错不一定是模型“不会回答”。也可能是：

- 相关内容没有被检索出来；
- 切分时丢失了标题、表格结构或上下文；
- 多份材料彼此冲突，系统没有识别版本；
- 找到的是相似材料，但不适用于当前部门或场景；
- 模型把检索到的片段错误地拼接起来。

![image-20261020092507541](%E4%B8%80%E6%96%87%E6%90%9E%E6%87%82%E7%9F%A5%E8%AF%86%E5%BA%93%E7%9A%84%E6%8A%80%E6%9C%AF%E6%BC%94%E8%BF%9B%EF%BC%9A%E4%BB%8E%E5%85%B3%E9%94%AE%E8%AF%8D%E6%A3%80%E7%B4%A2%E3%80%81%E5%90%91%E9%87%8F%20RAG%20%E5%88%B0%20GraphRAG%E3%80%81LLM%20Wiki%E3%80%81%E6%9C%AC%E4%BD%93%E8%AE%BA%E4%B8%8E%20Agent.assets/image-20261020092507541.png)

## 4. 混合检索与重排序：改进 RAG 的召回和排序

这些手段主要改进“找什么、把什么排在前面”。它们很有价值，但仍然不能自动解决定义冲突：一个 CRM 的客户记录和一个合同中的签约主体，是否代表同一个企业实体，不能单靠排序得分决定。

![image-20261020104824258](%E4%B8%80%E6%96%87%E6%90%9E%E6%87%82%E7%9F%A5%E8%AF%86%E5%BA%93%E7%9A%84%E6%8A%80%E6%9C%AF%E6%BC%94%E8%BF%9B%EF%BC%9A%E4%BB%8E%E5%85%B3%E9%94%AE%E8%AF%8D%E6%A3%80%E7%B4%A2%E3%80%81%E5%90%91%E9%87%8F%20RAG%20%E5%88%B0%20GraphRAG%E3%80%81LLM%20Wiki%E3%80%81%E6%9C%AC%E4%BD%93%E8%AE%BA%E4%B8%8E%20Agent.assets/image-20261020104824258.png)

## 5. 知识图谱与 GraphRAG：让检索能沿着关系走

图检索扩展了 RAG 的关联能力，但图谱质量决定了它能否给出有用的关联。边的名字也不能自动解释业务含义：“负责”可能表示项目 Owner、技术负责人、财务负责人或法律责任人。**若定义含糊，图能提供连接，却未必能提供正确解释。**

![image-20261020105130473](%E4%B8%80%E6%96%87%E6%90%9E%E6%87%82%E7%9F%A5%E8%AF%86%E5%BA%93%E7%9A%84%E6%8A%80%E6%9C%AF%E6%BC%94%E8%BF%9B%EF%BC%9A%E4%BB%8E%E5%85%B3%E9%94%AE%E8%AF%8D%E6%A3%80%E7%B4%A2%E3%80%81%E5%90%91%E9%87%8F%20RAG%20%E5%88%B0%20GraphRAG%E3%80%81LLM%20Wiki%E3%80%81%E6%9C%AC%E4%BD%93%E8%AE%BA%E4%B8%8E%20Agent.assets/image-20261020105130473.png)

## 6. LLM Wiki：从每次检索重组，到持续整理知识

普通 RAG 通常在每次提问时，从原始资料中重新检索相关片段，再由模型组织答案。LLM Wiki 采用另一种思路：**模型读入新资料后，持续更新一组互相链接、可供后续查询的知识页面。**

![图片](%E4%B8%80%E6%96%87%E6%90%9E%E6%87%82%E7%9F%A5%E8%AF%86%E5%BA%93%E7%9A%84%E6%8A%80%E6%9C%AF%E6%BC%94%E8%BF%9B%EF%BC%9A%E4%BB%8E%E5%85%B3%E9%94%AE%E8%AF%8D%E6%A3%80%E7%B4%A2%E3%80%81%E5%90%91%E9%87%8F%20RAG%20%E5%88%B0%20GraphRAG%E3%80%81LLM%20Wiki%E3%80%81%E6%9C%AC%E4%BD%93%E8%AE%BA%E4%B8%8E%20Agent.assets/640.webp)

## 7. 本体论与语义层：统一业务概念和关系定义

**本体论（Ontology）** 可以用来明确一个领域里的概念、属性、关系及其语义约束。以标准化的 <font color="#ffc000">OWL（Web Ontology Language，Web 本体语言）</font> 本体语言为例，它能够定义类、个体、属性及其语义。

它与知识图谱的关系可以这样理解：

- **本体或语义模型：定义概念和关系应该如何理解。**
- **知识图谱：记录具体对象及其事实。**

![图片](%E4%B8%80%E6%96%87%E6%90%9E%E6%87%82%E7%9F%A5%E8%AF%86%E5%BA%93%E7%9A%84%E6%8A%80%E6%9C%AF%E6%BC%94%E8%BF%9B%EF%BC%9A%E4%BB%8E%E5%85%B3%E9%94%AE%E8%AF%8D%E6%A3%80%E7%B4%A2%E3%80%81%E5%90%91%E9%87%8F%20RAG%20%E5%88%B0%20GraphRAG%E3%80%81LLM%20Wiki%E3%80%81%E6%9C%AC%E4%BD%93%E8%AE%BA%E4%B8%8E%20Agent.assets/640-17930825386942.webp)

## 8. Agent：从回答问题到调用工具和执行流程

Agent 在知识库演进中代表了另一种能力扩展：系统不只提供答案，还可能调用工具、查询业务状态、执行操作。**回答可以容忍一定的不确定性，执行操作则需要更明确的校验。**因此，从 RAG 走向 Agent，系统必须更加重视权限、审计、来源和执行前校验。

![图片](%E4%B8%80%E6%96%87%E6%90%9E%E6%87%82%E7%9F%A5%E8%AF%86%E5%BA%93%E7%9A%84%E6%8A%80%E6%9C%AF%E6%BC%94%E8%BF%9B%EF%BC%9A%E4%BB%8E%E5%85%B3%E9%94%AE%E8%AF%8D%E6%A3%80%E7%B4%A2%E3%80%81%E5%90%91%E9%87%8F%20RAG%20%E5%88%B0%20GraphRAG%E3%80%81LLM%20Wiki%E3%80%81%E6%9C%AC%E4%BD%93%E8%AE%BA%E4%B8%8E%20Agent.assets/640-17930841884814.webp)

## 这条技术路线不是瀑布式升级

前面的路线展示的是知识系统可能增加的能力，不代表企业必须从第一步一路建到最后一步。

实际架构经常是并行组合：

- 制度问答：全文搜索 + RAG，保留文档权限与引用。
- 跨文档研究：RAG + LLM Wiki，兼顾来源检索和持续综合。
- 客户与订单分析：结构化数据 + 知识图谱 + GraphRAG。
- 跨系统业务 Agent：语义层 + 业务 API + 权限校验 + 审计记录，必要时再结合 RAG。

LLM Wiki 不是 GraphRAG 的前一代或后一代；本体论也不是所有系统在 GraphRAG 后都要添加的模块。它们各自回应不同的工程需求。

## 怎么判断该引入哪种技术？

可以从问题类型开始，而不是从技术名词开始：

- 如果用户主要要找明确条款、编号或原文，先做好全文检索和元数据过滤。
- 如果用户用自然语言提问、资料表达方式不固定，考虑向量检索和 RAG。
- 如果问题需要从多份资料中关联实体和关系，评估知识图谱或 GraphRAG。
- 如果知识需要持续整理、跨材料形成可复用页面，尝试 Wiki 式知识编译，并保留来源和更新机制。
- 如果不同部门和系统对关键业务词定义不一，建立小范围、可治理的语义模型。
- 如果系统需要执行查询或操作，再增加 Agent、权限控制、业务规则和执行校验。

建议先选一个边界清晰、能衡量效果的场景，再逐步扩展。比如，从“客户—合同—订单”出发，先判断现有检索能否回答实际问题，再决定是否需要图关系、统一概念或 Agent 操作。不要为了技术完整而把每个组件都装上。

## 结语：知识库从搜索系统，走向可计算的知识基础设施

知识库技术的发展，核心不是一代技术淘汰上一代，而是系统逐渐能处理更复杂的知识问题：

**关键词检索找到词，向量检索找到相似表达，RAG让模型利用外部资料，GraphRAG沿关系检索，LLM Wiki持续整理知识，本体论统一业务语义，Agent在规则约束下使用知识完成任务。**

对技术人员来说，选型时可以记住三个问题：

**1. 知识以什么形式存在？**文档、数据库记录、图结构，还是经过持续整理的页面？

**2. 系统要完成什么任务？**搜索、问答、跨实体推理，还是执行流程？

**3. 结果如何验证和治理？**来源、权限、版本、冲突和更新机制是否明确？

把这三个问题回答清楚，通常比单纯追逐“最新的知识库架构”更能帮助团队做出合适的技术选择。
